# ADR 0017: Централизованный контроль OpenWrt-роутеров

**Статус:** Принято для реализации
**Дата:** Сентябрь 2026

## Контекст

Роутеры находятся за NAT и подключаются к одному из трёх gateway-серверов по
reverse SSH. На каждом gateway исторически работала отдельная копия
`tunnel-monitor`. Это создаёт дублирование Telegram-бота и разрозненное
состояние.

## Решение

Оставить один Telegram Bot и один Monitor на центральном сервере. Monitor
подключается к gateway по SSH, затем к `127.0.0.1:220x` роутера. Все события,
временные ряды и команды хранятся централизованно.

PostgreSQL используется для состояния, истории событий и audit log; Prometheus
и Grafana/Alertmanager — для time-series и визуализации. На роутеры не ставится
мониторинговый агент на первом этапе.

Функциональный критерий VPN — иностранный egress IP, подтверждённый двумя
endpoint'ами. Process/procd/`tun0` остаются диагностическими сигналами.

## Альтернативы

- Копия бота на каждом gateway — отклонено из-за дублей и расхождения состояния.
- Постоянный агент на каждом роутере — отложено из-за ограничения ресурсов.
- Zabbix agent/Netdata на роутерах — отложено до доказанной необходимости.
- Публичный management-порт — отклонено; reverse SSH уже решает NAT-задачу.

## Последствия

Центральный сервер становится единой точкой хранения и уведомлений. При его
недоступности data plane роутеров не меняется, но новые проверки и команды
временно недоступны. Мониторинг должен иметь bounded retries, cooldown и
backup PostgreSQL.
